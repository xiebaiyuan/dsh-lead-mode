# 多轮长程控制回路

只在预计 ≥2 轮派单/验收、或跨模块持续推进的长程任务里读。单轮任务（一人一轮干完、无跨轮合流）不用打开。

## 1 何时启用

满足任一条就启用这套控制回路：

- 预计需要 ≥2 轮派单或验收才能交货。
- 改动跨多个模块，存在先后依赖或合流节点。
- 任务已进入第 2 轮，主目标判据尚未全部通过。

不启用：单成员一轮做完、纯资料查询、无跨轮状态的小改动。

完成标准：开工前判清「启用 / 不启用」；启用后列出主目标判据编号 `#1..#M`。

## 2 主目标判据进度账（N/M）与工具边界

开工前把主目标拆成 `M` 条可验证判据（编号 `#1..#M`），每条写明核验命令或可复现判据。派单与工作日志的状态摘要都标明级别（主目标 / 支撑 / 枝节）与服务判据 `#k`；支撑活额外写明阻塞哪条主目标判据与停止线，解除阻塞即止。

每轮醒来，先算已通过的主目标判据数 `N/M`：

- 只有带证据（可粘贴命令 + 输出摘要，或独立验收核验结果）的判据才计入 `N`。
- 口头声称「已通过」「已修好」不计入 `N`。
- 未达成的主目标判据与阻塞它们的支撑活排在最前；枝节回报直接记入 `.scratch/<effort>/leftovers.md`，不占 `N/M`、不进并行队列。

轻量工具与落盘边界（不造第二份正文）：

| 工具 / 文件 | 怎么用 | 边界 |
|---|---|---|
| `todo_write` | 可选，一判据一条，轻量跟踪 `#1..#M` 的 `N/M` 进度 | 只放主目标判据；不把枝节、临时想法塞进 todo |
| `create_goal` | 仅在用户明确要求无人值守长程推进时启用 | 普通多轮协作不默认开；用户没授权就不调 |
| `.scratch/<effort>/worklog-<mate>.md` | 成员滚动进度与死路记录 | 每位成员一份，不另开每轮总表 |
| `.scratch/<effort>/leftovers.md` | 枝节与降级验收台账 | 五列表格，收尾报数 |
| `reports/<YYYY-MM-DD>-<effort>.md` | 收尾一次成型的团队汇总（见 `team-digest`） | 不新增 `reports/status-*.md` 或独立 `acceptance.md`（遵循 ADR 0001，避免多份正文漂移） |

完成标准：每轮醒来报得出当前 `N/M`；todo 里只有 `#1..#M`；磁盘上不出现 `reports/status-*.md` 或独立 `acceptance.md`。

## 3 分层验收与验收预算

验收分两层，避免每改一个小模块就全量重跑：

| 层次 | 什么时候跑 | 跑什么 | 默认次数上限 |
|---|---|---|---|
| 局部验收 | 每个中间轮次结束 | 受影响子集：目标单测、局部 check、本块文件 `git diff --stat` | 每轮按块跑，过单即放行 |
| 全量验收 | 关键合流节点、最终交货前 | 全套测试、全量 check、跨模块回归与最终 diff | 默认最多 **2 次**（合流 1 次 + 最终独立验收 1 次） |

三条护栏：

1. **判据全过即停**：任务单既有判据 `#1..#M` 全部通过，且无新发现的阻塞性主目标缺陷，立刻收工，不顺手加检。
2. **独立验收只核既有判据**：最终独立验收成员只核任务单既有判据与主目标直接相关回归；顺带发现的枝节或范围外改进按级写入 `.scratch/<effort>/leftovers.md`，不扩大验收范围，不触发额外返工。
3. **降级验收可写走查步骤**：全量视觉回归、逐条界面走查等难以一条命令覆盖的项，允许降优先级入 `leftovers.md`；「后面怎么查」一列除可粘贴命令或文件路径外，可写可复现走查步骤（**对象 + 入口 + 判据**）。三条都写不出来就不许降级。

完成标准：中间轮次不反复跑全量；全量验收默认 ≤2 次；独立验收不因范围外发现加派返工单。

## 4 连续 2 轮无增长：先升模型，再止损问用户

**触发条件**：连续 2 轮派单/验收结束时，主目标判据通过数 `N` 没有增长（`N` 停在同一个数）。

按以下三步顺序执行，不跳步、不原地无限重试：

1. **停枝节、查授权模型清单**：立刻停止新派任何枝节单。调用 `list_subagent_models()` 检查当前会话授权清单里，是否有比现用执行成员更强的模型（例如 Opus 等旗舰推理模型，或更高推理档如 `high` / `max`）。`provider`、`model`、`reasoning_effort` 一律从 `list_subagent_models` 返回原文逐字抄写，严禁编造 id；两层开关与老版本会话钉住规则见 `references/member-models.md`。
2. **有更强模型 → fresh 接手卡点跑 1 轮**：把卡住的主目标判据 `#k` 或阻塞支撑整理成交接文档（或窄任务单，写明已排死路与绝对路径），用 `subagent`（`fresh`，不用 `subagent_fork`——fork 不带模型参数且拷的是 Lead 历史，拿不到前任细节）切换到更强模型跑 1 轮，验收并核查 `N` 是否增长。
3. **无更强模型，或切后仍无增长 → 停派问用户**：授权清单里没有更强模型（例如只返回一条跟随父模型，或现用成员已是清单最高档），或者按第 2 步切更强模型跑完 1 轮后 `N` 依然无增长时，立刻停下新派单，向用户汇报四项并等拍板：
   - 当前进度 `N/M` 与卡住的判据 `#k`；
   - 已尝试的路径与排除的死路（写明是否已尝试切更强模型、用了哪一对路由或为何无法切换）；
   - 2–3 个可执行取舍选项：降范围（砍哪条判据）/ 调判据 / 用户人工介入 / 在设置页「子智能体 → 模型选择」授权更强模型后新开会话重试；
   - 未解决项的当前风险。

与主文件 §12「难度升级：一次同模型专家」的分工：同模型专家只用于单件设计/审美/架构类判断力任务退回两次后出方案不动手；本节用于多轮长程中 `N` 停滞时升级执行成员模型直接突破卡点，或在无更强选项时止损请示用户。

完成标准：连续 2 轮 `N` 无增长时，先看 `list_subagent_models` 决定切模型还是止损；切后仍停滞或无可切时，带着四项汇报停手问用户，不空转第 3 轮。

## 5 Lead 上下文压缩后重锚

长程任务跑多轮后，Lead 自己的会话也会被自动压缩，早期目标、判据编号和已排除的枝节可能只剩摘要。

每次 Lead 自身发生压缩，或隔轮醒来发现上下文变薄时，先做三步重锚，再决定下一轮派单：

1. **核主目标判据（N/M）**：重核 `#1..#M` 哪些已带证据通过、哪些未过、是否已连续 2 轮无增长（用了 `todo_write` 看 todo，没用就看任务板与各成员工作日志头部状态摘要）。
2. **核任务板在办项**：调 `team_task_list` 对照在办任务、阻塞关系与最新 `revision`，确认当前仍在阻塞主目标的支撑活。
3. **核遗留清单**：派只读成员核对 `.scratch/<effort>/leftovers.md` 现状（只缺一两条记录时可直接核查），确认哪些问题已归枝节，避免压缩后把已降级的旧枝节重新派成新单。

硬边界：重锚完成前不派新单；绝不顺着最近一条枝节通知往下挖。

完成标准：每次压缩或隔轮醒来后，能准确说出当前 `N/M`、剩余未过判据 `#k` 与在办主目标/支撑任务，再发出下一轮派单。

## 6 多轮样例：3 轮跨模块改造

场景：给导出模块增加 CSV 编码修复与断点续传，跨 `parser/`、`exporter/`、`ui/` 三个目录。

开工定下 3 条主目标判据（`M = 3`），用 `todo_write` 记 3 条（不放枝节）：

- `#1`：`parser/` 正确识别 UTF-8 BOM 与 GBK 输入（`npm test -- test/parser.test.mjs` 全绿）
- `#2`：`exporter/` 中断后可按偏移量续传且无重复行（`npm test -- test/exporter.test.mjs` 全绿）
- `#3`：整套集成测试与打包检查全绿（`npm test && npm run check` 通过，且最终 diff 无范围外改动）

### 第 1 轮：判级、并行派主目标、拦下枝节

- 拆出 4 块活：
  - `task-1`（主目标｜服务 `#1`）：改 `parser/`。
  - `task-2`（主目标｜服务 `#2`）：改 `exporter/`。
  - `task-3`（支撑｜阻塞 `#2`｜停止线：提供临时断点文件读写 helper 即止，不重构存储层）：补 `shared/checkpoint.mjs`。
  - `ui/` 导出进度条小屏文案截断（枝节）：写作用域虽与前 3 块不重叠，但先按 §12 判级为枝节，**不进并行队列**，直接记进 `.scratch/20261124-export/leftovers.md`：
    - 编号 1｜导出进度条小屏文案截断｜不影响主目标验收｜对象：导出弹窗进度条；入口：打开导出页并将窗口宽度缩至 360px；判据：进度百分比与按钮文案不重叠、无截断｜发版前
- 派单：`task-1` 与 `task-3` 无依赖，一次并行派给 `parser-dev`、`infra-dev`；`task-2` 标 `blocked_by: ["task-3"]`。派完结束回合。
- 醒来核进度：`parser-dev` 交卷且局部测试通过（`#1` 通过），`infra-dev` 解除阻塞并按停止线收手。当前 `N/M = 1/3`（本轮有增长：`0 → 1`）。派 `exporter-dev`（普通档模型）执行 `task-2`。

### 第 2–3 轮：局部失败、连续 2 轮无增长触发模型升级

- **第 2 轮醒来**：`exporter-dev` 交回 `task-2`，但局部单测 `test/exporter.test.mjs` 在并发重入场景失败，`#2` 未过。当前 `N/M = 1/3`（第 1 轮无增长）。Lead 明确指出失败用例与报错，重发窄单给 `exporter-dev` 返工。
- **第 3 轮醒来**：`exporter-dev` 返工后仍卡在同一边界条件，`test/exporter.test.mjs` 依旧红，`#2` 未过。当前 `N/M = 1/3`（**连续 2 轮无增长**，触发 §4 升级止损）。
- Lead 执行 §4 三步：
  1. 停新派任何枝节单；调 `list_subagent_models()`，发现清单里除现用普通档模型外，还授权了旗舰推理模型（如 Opus `high` 档，原文抄写 `provider` / `model` / `reasoning_effort`）。
  2. 要求 `exporter-dev` 补完工作日志并写交接文档 `.scratch/20261124-export/handoff-exporter-dev-1.md`（含已排死路），release `task-2` 后用 `subagent`（`fresh`）切旗舰模型派 `exporter-dev-r2` 接手跑 1 轮。
  3. `exporter-dev-r2` 一轮定位偏移量锁竞争，局部测试 `test/exporter.test.mjs` 全绿，`#2` 通过。进度突破至 `N/M = 2/3`。（若清单里没有更强模型，或 `exporter-dev-r2` 跑完后仍停在 `1/3`，Lead 直接停派并按 §4 第 3 步请示用户拍板。）

### 收尾：最终独立验收，过即停

- 派未参与实现的只读成员 `verifier` 执行最终独立验收（全量预算 1/2）：只核 `#1`、`#2`、`#3` 与主目标直接回归，运行 `npm test && npm run check` 与 `git diff --stat`。
- `verifier` 回报 `#1/#2/#3` 全部通过（`N/M = 3/3`），顺带提到 `exporter/` 有一处老日志格式不够整齐。Lead 判为范围外枝节，记入 `leftovers.md` 编号 2，不触发额外返工，直接按 `team-digest` 写团队汇总并交货；收尾报数：`主目标：达成（3/3）`，遗留 2 条在 `.scratch/20261124-export/leftovers.md`。
