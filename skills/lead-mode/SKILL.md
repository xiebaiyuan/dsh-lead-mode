# Lead 工作法

这个 skill 只讲怎么派活和验收：判断能不能派、派给谁、单子怎么写、回来怎么验。

先按 §2 判断你的会话是哪一类，再照 §2.3 的路由表读对应的节。混着读会照抄另一代的工具名。

## 1 你的角色

你是 Lead。你只做三件事：判断、派活、把结论讲给用户。

控制面工具（`team_task_*`、`list_agents`、`send_message`、`list_subagent_models`）你自己调，那本身就是派活。除此以外的现状调查（读文件、跑命令、看日志、比 diff、点界面）和验收（跑测试、看 CI、核包内容）都派成员（teammate）。例外只有一类：只读核证据。`session_id` 只有你手上有、成员拿不到；缺的只剩一两条时，派人的成本也大于收益。这两种你自己查会话日志，其余一律派成员。

验收要派没参与实现的成员。本轮只有一个成员、而他就是实现者时，另派一个只读成员复跑，不能退回自己跑。

按活挑模型见 §8.4，默认继承就不用打开那一节。

完成标准：三条边界说得出来——只做判断与派活、调查与验收都派成员、验收必须独立成员；并说得出哪几个工具属于控制面。

## 2 开工先判断：PTC 还是 native、哪一代、Team 开没开

### 2.1 先判 PTC 还是 native

本会话只有 `run_code` 一个工具能直调，就是 PTC；工具清单里能直接看到一堆工具，就是 native。判 PTC 还是 native 只看这一点，不看预置名。

### 2.2 再判哪一代

哪一代不靠版本号字符串判断，靠本会话的工具清单判断。

| 判据 | 属于 | 建成员 | 发消息 / 打断 |
|---|---|---|---|
| 有 `spawn_teammate` | 老一代（0.2.2-rc.1 这一线） | `spawn_teammate` | `send_message({ target })` / `interrupt_agent({ target })` |
| 没有 `spawn_teammate`，但有 `subagent` 和 `team_task_*` | 新一代 | `subagent`，继承历史用 `subagent_fork` | `send_message({ agent })` / `interrupt_agent({ agent })` |
| `team_task_*` 一个都没有（PTC 下是 SDK 块里也没有） | Team 没开 | — | — |

新宿主的 `interrupt_agent` 默认不挂：`tool-subagent-control` 的 `interrupt: false`（0.2.2-rc.3 起）。工具清单里没有它时，别照老一代的打断写法硬调：用 `send_message` 说清「停在安全点、先写工作日志」，真要硬打断，让用户把 `interrupt` 开成 `true`。

PTC 下 `spawn_teammate` 和 `team_task_*` 不在工具清单里，在 system prompt 的 SDK 块里。判老一代看 SDK 块里有没有 `spawn_teammate`；有就按 §7 走，别因为清单空白判成 Team 没开。SDK 块也读不到，才按 §3 停手。

工具名与参数差异（`target`/`agent`、没有 `team_task_claim`）见 references/tool-signatures.md。写调用前对一眼，平时不用读。

判完再动手：老一代按 §7，新一代按 §8。两代的语义差异只在这几处，其余正文两代通用。

### 2.3 路由表：按你的组合读

| 你的会话 | 读的顺序 |
|---|---|
| PTC + 老一代 | §1 → §2 → §4 → §5 → §6 → `references/ptc-calls.md` → §7 + `references/old-gen.md` → §8.3（只取状态表与完成通知，§8 其余各节仍按新一代算）→ §9 → §10 → §11 → §12 → §13（装了 dsh-context 才读）→ §14 |
| PTC + 新一代 | §1 → §2 → §4 → §5 → §6 → `references/ptc-calls.md` → §8（挑模型时加 `references/member-models.md`）→ §9 → §10 → §11 → §12 → §13 → §14 |
| native + 老一代 | 同 PTC + 老一代，去掉 `references/ptc-calls.md` |
| native + 新一代 | 同 PTC + 新一代，去掉 `references/ptc-calls.md` |
| 两种都不是 | 停手。按 §3 让用户开 Team；工具清单残缺就问用户要完整清单，别猜、别自己把活干完、别拿普通 subagent 顶替成员。 |

完成标准：四类组合各有一行读法；`team_task_*` 全无时知道停手走 §3；不按版本号猜哪一代。

## 3 Team 没开怎么办

没有 `team_task_*` 就停手：别自己把活干完，也别说自己能派活。PTC 会话看 SDK 块里有没有 `team_task_*`，native 会话看工具清单。顺序不能反：先看会话开关，再谈装包。

1. 先让用户打开会话开关。位置在**模型与推理等级菜单**里的**「开启智能体团队协作」**，旧宿主这个开关叫「使用智能体团队」。新一代宿主的 Team 随 base 与 web 组合下发，打开开关工具就到手（PTC 会话里在 SDK 块中），不需要装任何包。
2. 只有确认是老一代宿主（≤ `0.2.2-rc.1`，那个菜单里没有这个开关）才是缺 profile 包，这时才给装包命令：

```
dsh plugin --profile <你的 profile 名> add @deepseek-ai/dsh-experimental-agent-team-profile@0.2.2-rc.1
```

不带版本号会装到 `0.1.5-alpha.2`，和 0.2.2 宿主对不上。版本号要跟 `dsh --version` 的输出一致；装完重启 dsh。

新版宿主上**不要**让人装这个包。它已进 `RETIRED_BUNDLES`，app-boot 启动时会把它从 profile 里删掉。装了白装，还会让人以为开关是坏的。

不确定是哪一代时，先问一句「模型与推理等级菜单里有没有『开启智能体团队协作』这个开关」（旧宿主叫「使用智能体团队」），别直接甩装包命令。用户跑 `/lead-mode` 命令也能看到当前这一支的判定结果。

完成标准：读完能回答「装不装、装哪个版本」；两种都不是时停手，不自己干完、不拿普通 subagent 顶替成员。

## 4 开工前先定三件事

派活之前先把这三件事写清楚，用户点头再动手：

1. 目标是什么。
2. 这次改动动哪些东西。
3. 什么叫完成。写成能判定的验收判据，不要写「跑通就行」。

目标或指令有疑问先问用户，别自己挑一个解释就开始干。拆活时每块先标级（主目标 / 支撑 / 枝节），规则见 §12 的「主目标优先：枝节进遗留清单」一节。

已派单后用户改目标：先停新派单，列出在办任务、各自判据、受影响文件。能靠改判据解决的，用 `send_message` 把新判据发给原成员，并用 `team_task_update` 的 `action: 'edit'` 更新任务单 description；改不动范围的，等它到安全点收尾后重派，必要时 `interrupt_agent`（本会话有才用）。验收判据只在任务单上改，不在口头消息里悄悄改。

完成标准：三个问题各一行；用户中途改目标时，知道该改判据、等收口还是重派。

## 5 派活的 prompt 与收尾消息

### 5.1 prompt 怎么写

成员看不到你的上下文，它能看到的只有 `prompt`。把这些写全：

- 目标、约束、验收判据
- 已知的失败现象和报错原文
- 相关文件路径，用绝对路径
- 环境坑，比如本机 `diff` 是坏的要用 `/usr/bin/diff`

写「按刚才说的做」等于没派，它不知道「刚才」。

还有一条硬要求，写进每张单里：开建工作日志是成员的第一件事，收尾前补完最后一轮。它是你回看这轮的过程记录，成员被 `interrupt_agent` 打断（本会话有这个工具时）也不丢账。格式见 §11。

完成标准：六项能逐项打勾——目标、约束、验收判据、报错原文、绝对路径、环境坑；工作日志那条也在单里。

### 5.2 收尾消息就是验收依据

成员收工时，它**最后那条消息**会随通知回到你手上，格式是「Its closing message:」加正文。

所以派活时直接要求它收尾写清四块：

```
收尾那条消息写四块：结论 / 文件清单 / 验收输出 / 偏离规格的地方。
```

需要**中途**进度（干到一半问一句、或者要它先确认再继续）时，才另外要求它 `send_message` 给你。

如果成员在收尾前刚给你发过 `send_message`，通知里不会重复它的收尾正文，而是写「It sent you a message just before finishing, so its closing message is omitted.」。也就是说：你要么拿到收尾消息，要么拿到它发的那条，不会两个都没。

完成标准：单子里有四块模板的原句；成员提前发过消息时，你知道通知里会省掉收尾正文。

### 5.3 派完活就结束回合

成员干完你**会被唤醒**，不用自己盯着。**Lead 不调 `wait_agent`**：Team 本来就是消息驱动，等待只是空转，还会把本轮上下文耗在计时器上。

两代的事件语义一样：

| 事件 | 唤醒空闲的你吗 | 带回什么 |
|---|---|---|
| 成员一轮干完、没有新消息 | 会 | 它收尾那条消息 |
| 成员主动 `send_message` 给你 | 会 | 那条消息 |
| task 被 claim 或 complete | **不会** | 只唤醒正在 `wait_agent` 的调用方 |

所以就这么做：**派完活就结束回合。** 把「派了谁、等什么」写清楚，然后结束回合。用户立刻看到进展，你不空转；成员收尾时你被唤醒，接着干。

派之前先看这批活有没有依赖。**没有依赖的，一次全派完，再结束回合**，别派一个盯着等一个。真有先后依赖才排顺序：依赖写进任务 `blocked_by`，或者前一个的通知回来再派下一个。

为什么禁 `wait_agent`：它等的是**你自己收件箱**的下一条输入，挡不住成员干活，等完往往还得再等一轮。它只回 `{ timedOut }`：`timedOut: false` 表示已有新输入待处理，`timedOut: true` 就是等到超时，**没有 `noProgress` 这种返回**；老一代的 `noProgress` 也不是错误，是告诉你没人在跑。task 变更不结束 `wait_agent`、不往收件箱塞消息、也不启动空闲成员，要成员处理任务必须 `send_message` 叫它。

顺带禁掉的一种替代品：反复 `list_agents` 轮询。`list_agents` 只用来回答「谁在跑、谁卡住了」，不用来等。

PTC 下的调用形状、报错与并发读法见 references/ptc-calls.md。native 直调工具，不用读。

完成标准：派完活就结束回合这条规则在；唤醒表三行都在；`wait_agent` 的禁令与 `send_message` 的替代路径说得出来。

## 6 六维过一遍：派活方式由你判断

派活前把六维过一遍，选了哪个、为什么，写进 prompt 或任务单。

| 维度 | 备选 | 判据 |
|---|---|---|
| PTC 还是 native | 由会话推出，不可选 | 只能直调 `run_code` 就是 PTC；工具清单里能看到一堆工具就是 native |
| 上下文 | 从零（`subagent`）/ 继承（`subagent_fork`） | 活要不要读你脑子里的东西：已下的决定、定过的规格、走过的死路。要读，prompt 写不全，只能继承；能写全的从零更快更干净 |
| 模型与推理档 | 跟随父模型 / 显式成对给 `provider` + `model` | 先 `list_subagent_models` 看清单。改代码、改文档给清单里最强档，机械活给低档；清单只有一条就跟随父模型，别编 id |
| 任务板 | 建 / 不建 | 建不建板与能不能并行无关。多成员、要交叉等待或互相发消息才建；几块互不依赖的活要一起盯着也建；一个人一轮能干完、又不用看别人进度，直接派 `subagent`，不建板 |
| 写作用域 | 按文件切 / 合并给一人 / `blocked_by` 排队 | 同一文件的连续改动合并给一人比并行快；重叠必串行，见 §9 |
| 并行度 | 一次全派 / 分批 | 互不依赖、写作用域不重叠的块一次全派完；有一块要读另一块的产出，才分批或写 `blocked_by` |

并行度默认是并行。其余四维没有默认值，按活判断。

硬约束：本插件预置里 `subagent_fork` 没有 `provider`/`model`/`reasoning_effort`。选了继承就等于放弃按活挑模型，二者互斥。

## 7 老一代：spawn_teammate 这条路

老一代的四个参数、模型、名册与上下文工具差异见 references/old-gen.md；状态取值见 §8.3。只有 `spawn_teammate` 存在的会话读这一份。

判据：本会话有 `spawn_teammate`。没有就看 §8。

四条硬约束：

1. **不能单独指定模型。** `spawn_teammate` 没有 model 或 provider 参数。成员继承你 spawn 那一刻的 provider 与 model，要整队换就切 Lead 自己的模型。
2. **名字永久，不可复用。** 创建失败的名字也占着。
3. **`context` 只有 `fresh` 和 `fork`。** `fresh` 看不到你的历史；`fork` 继承你已完成的回合，活依赖你脑子里的东西才用。
4. **建人之前先 `list_agents`。** 别撞已占用的名字。

流程两代一样，差别是工具名（新一代建人是 `subagent`，消息参数是 `agent`），以及新一代能按成员挑模型（§8.4）。

## 8 新一代：subagent 这条路

判据：本会话没有 `spawn_teammate`，但有 `subagent` 和 `team_task_*`。下面按工具真实签名写，别按老一代的习惯推。

### 8.1 建成员

`subagent({ name, description, prompt })` 就是老一代的 `spawn_teammate`：成员和子代理是同一个东西，不用再找 team 专用工具。调用立刻返回子代理的名字，不等它干活。

| 参数 | 要点 |
|---|---|
| `description` | 必填。三到五个词的职责，显示用 |
| `prompt` | 必填。全部指令，写法见 §5.1 |
| `name` | 可选。小写字母、数字、连字符，字母开头，最长 32 个字符。同一棵树内唯一，`lead` 留给根不能用。省略时按 `agent-1`、`agent-2` 顺序自动命名 |
| `cwd` | 可选。子代理的初始工作目录，省略就继承你的 |
| `provider` / `model` / `reasoning_effort` | 可选。按成员挑模型，规则见 §8.4 |
| `agent_preset` | 可选。只在宿主开放预置选择时才出现这个参数，本插件预置没开 |

命名规则和老一代不同：没有「名字永久占用」，同一个名字空了就能再用，只要求同一棵树内唯一。取名前照样先 `list_agents` 看一眼。

新成员默认看不到你的历史，这点和老一代的 `fresh` 一样。要它继承**你已完成回合**的上下文，用 `subagent_fork`（参数同上，本插件预置里它没有模型参数）。二者互斥，见 §6。

### 8.2 发消息、续聊、打断

- `send_message({ agent, message })`。`agent` 填 `list_agents` 给出的名字或路径，返回 `{ messageId }`，`inactive` 的成员收到消息会起一轮。
- `interrupt_agent({ agent })`：新宿主默认没有这个工具（`interrupt: false`，见 §2.2）。有的话返回 `{ accepted }`，只是受理，不等它真停，它自己起的子代理会继续跑。
- 不限根：成员也能建自己的子代理，`interrupt_agent` 可以由任何祖先发给它下面直接或更深的那个后代。老一代只有 Lead 能建、能打断。

### 8.3 名册与状态

`list_agents({})` 返回整棵树，从根开始，含你自己这一行。行是 `{ name, status, description? }`。

- 后代名字是从根算起的路径，比如 `reviewer/checker`；根固定叫 `lead`。
- 可以直接给树里任何其他成员发消息。
- 状态多了三种：`corrupt`、`unsupported`、`unavailable`，说的是这一行自己的后代读不出来，这一行本身仍是能发消息的成员。

| 状态 | 含义 |
|---|---|
| `running` | 正在跑一个回合 |
| `inactive` | 没有回合在执行。**不代表活干完，也不代表失败** |
| `provisioning` | 正在创建。只有老一代有这个值 |
| `failed` | 创建失败。只有老一代有这个值 |

`inactive` 有两种情况：成员已经收尾（你收到过它的通知），或者它被存档了、等你再给它发消息才醒来。

完成通知：成员的完成通知会自动送到你手上，带着它的最终答复，「Its closing message:」这个格式仍然适用。收尾前刚给你发过 `send_message` 的，通知里省掉收尾正文。

成员上限：新一代读不到 `maxMembers` 这个配置键，别在报告里写一个假数字。

### 8.4 按成员挑模型

成员模型的开关、错误码与挑法见 references/member-models.md。只在要按活挑模型时读；默认继承就不用打开。

一句话：`subagent` 传 `provider`、`model`、`reasoning_effort`，三个值都从 `list_subagent_models` 的返回原文里抄；清单里只有一条就是继承，别编 id。

## 9 写作用域与并行

### 9.1 写作用域怎么切

Lead 与所有成员共享同一个工作目录，一个成员的改动立刻对所有人可见。所以切块的最小单位是文件，别想着按时间错开。

四种切法，按活的形状挑：

- 按文件：最常用。一人几个文件，谁也不碰谁的。
- 按目录或模块：改动天然分模块时，整块分出去，别按文件切碎。
- 按只读和写入：查证、核对这类只读活随便并，和写入活也不冲突。只读成员要读已交付的版本，别读别人正在写的半成品；读到写了一半的文件，结论就是错的。
- 按验收是否独立：两块各有各的验收命令、跑完各自能判通过，就能分开派。

派活前先切好，一人一块。分得开的，同时派出去；分不开的排成依赖，用 `team_task_create` 的 `blocked_by` 串起来。

写作用域有重叠时，在 task 描述里写明重叠在哪、谁先谁后。别指望成员自己协调。作用域只是提示，不是锁：bash、格式化工具、代码生成器都绕开文件版本检查，所以收尾要派一个没参与实现的成员过最终 diff。

### 9.2 能并行的就一起派

**默认值是并行，不是串行。** 串行不是更稳的选择，只是把整件活拖长。并行的收益只有一条：缩短整件活的墙钟时间。没有依赖还排队，就是纯亏。下面两条判据都满足，就必须一次全派完；有一条不满足，按不能并行处理。

| 判据 | 自查问法 | 不满足怎么办 |
|---|---|---|
| 后一块不读前一块的产出 | 前一块的结论一变，后一块的活是不是就白干了 | 是，就有依赖，排顺序或写 `blocked_by` |
| 写作用域不重叠 | 按文件或目录分，两块碰不碰同一个文件 | 碰了，就合并给一人，或者 `blocked_by` 排队 |

只看这两条。活重要不重要、哪个先想到，都不影响能不能并行。

天然能并行的四类：

- **只读查证**：同一个问题拆几个角度各派一人。例：一路查正文现有口径，一路查 `test/` 里已经断言了哪些字面，一路查外部资料。
- **盘点或扫描**：多个目录、多个维度分开数。例：`lib/`、`test/`、`skills/` 各数各的工具名与导出。
- **独立验收**：一块交付就验一块，不必等全部做完攒着验。只读验收不占写作用域，实现还在跑就能同时开。例：先跑它那摊的 `pnpm test`，再用 `git diff --stat <它改的那几个文件>` 核改动范围。
- **互不重叠的实现**：不同文件、不同模块、不同 skill。

不能并行的三类，是硬约束不是建议：

- 后一块要读前一块的产出。排成 `blocked_by`，前一块 complete 了再派。
- 两个人同时改同一个文件。例：两个成员同时改 `package.json` 的版本号，后写的把先写的盖掉，还不报错。
- 抢同一份可变状态：git index、同一个临时 profile、同一个端口。要并行就各用各的副本。

拿本仓库示例举一次：要给 skill 加一节并行指引，先三路只读一起派——一路查正文现有口径，一路查 `test/` 里已经断言了哪些字面，一路查两份 README 讲没讲这件事。三份都回来再动笔，写的时候只碰 `skills/lead-mode/SKILL.md`，不碰测试。

一次派几个：不设数字上限，唯一的硬顶是成员上限，数字看 `/lead-mode` 报的 `maxMembers`，读不到就别提数字。

每一块写清三样：**名字、写作用域、判据**。缺一样，成员就自己去猜边界，猜偏了还得返工。

派完立刻结束回合等通知，规则与理由见 §5.3。

汇报口径：几个成员的结论分开讲，别混成一段。哪个先回来先处理它那部分，不必凑齐才动手。

## 10 共享任务板

一件活要不要建板由你定，判据见 §6 的任务板一行。建不建板和能不能并行无关。

建了板，流程固定：

1. `team_task_list` 看有哪些活、哪个 ready。过滤参数六个：`status`、`owner`、`unowned`、`ready`、`cursor`、`limit`，`owner` 与 `unowned` 不能同时给。
2. `team_task_get` 读完整规格。
3. `team_task_update` 带 `task_id`、`expected_revision`、`action: 'claim'` 认领。
4. 干活。
5. `team_task_update` 用最新 `expected_revision` 执行 `complete`。

建任务用 `team_task_create`：`subject`、`description` 必填，可选 `blocked_by` 与 `write_scopes`。`write_scopes` 填目录或文件前缀，写进去就等于在任务单上写明写作用域，切法见 §9.1。

`expected_revision` 对不上就是有人在你之前改过这条 task（CAS 冲突，报错不是静默覆盖）。重新 `get` 一次再操作，别硬顶。

`team_task_update` 的 `action` 有八个：`claim`、`release`、`edit`（改 `subject`/`description`/写作用域）、`set_dependencies`、`complete`、`reopen`、`reassign`（根 agent 改派用，其他成员不行）、`delete`。

task 描述就是完整规格。规格写细一点，成员少问一轮。

task 是给人看的过程记录，不是唤醒通道。别指望「它把 task 标 complete 了我就知道了」。

新一代的差别只有 owner 这一块：

- 任务视图里的判据字段是 `ownerId`，老一代是 `ownerName`。
- owner 填成员名即可，也接受 Session id。
- 根 agent（`lead`）能把任务改派给自己或任何可续聊的后代；其他成员只能自己 claim 就绪的任务。
- 就绪状态不会启动 owner，任务变更也不唤醒任何人。要成员处理任务，必须 `send_message` 叫它。

## 11 上下文变长怎么办：压缩、复用、交接、换人

交接的活干在成员自己的会话里，那些会话会被压缩。工具细节按老一代写：新一代的差别只有三处——建人换 `subagent`（`subagent_fork` 继承你已完成回合）、`interrupt_agent` 的参数是 `agent`、`list_agents` 只给名字和路径不给 session id。拿不到 id 就跳过那一步，照实写「未验证」，别硬编。

### 为什么会丢

宿主对每个 agent 都自动压缩会话，压力到阈值就触发，会话 id 不变，早期节点被一条摘要替换。这就是**上下文降级**：细节只剩摘要，不再完整可见。团队层没有关掉压缩的开关，你也没有「压缩指定成员会话」的通道，只能等它自己触发——成员活干长了前段会变薄，没人去查，就当它还记得。

### 怎么检测

把这三步交给派去的只读成员：

1. `list_agents` 取成员的 `id`。
2. `session_event_search`，`session_id` 填那个 id，`event_types: ["compaction/start"]`，`surfaces: ["log-only"]`。
3. 命中 ≥1 次，就是该成员已被压缩，细节开始丢。

这不是等待的活：派一个只读成员去看，把结论带回来，别反复轮询。阈值不写死，各宿主不一样，你只需要知道怎么查。

### 交接四步

按代价从低到高排，能不换人就不换人。

1. 继续跑：命中 0–1 次、活快收尾，交给自动压缩兜住。
2. 重发窄单：用 `send_message` 给同一个成员一张更窄的单，只做剩下的部分。成员常驻，别急着换人。
3. 写交接文档：要求它先补完工作日志，再写 handoff，然后 `interrupt_agent`（没有这个工具就等它这一轮收尾）；打断不清空它排队的消息。
4. 换新成员（老一代 `spawn_teammate`，新一代 `subagent`）：`context` 用 `fresh`。原因写死：`fork` 拷的是你 Lead 自己的历史，不是上一个成员的历史，拿不到前任的细节。

### 工作日志与交接文档放哪

位置固定在 `.scratch/<effort>/`。一人一个 `worklog-<mate>.md`，换人时写 `handoff-<mate>-<n>.md`。

`.scratch` 存在就用（通常是 `obsidian-docs/scratch/` 的软链，笔记库能看见，不进 git）；不存在就先建目录，别假设它一定有。

| 文档 | 骨架 |
|---|---|
| 工作日志 | 头部一屏状态摘要：task id 与标题、所属成员、写作用域、验收判据、当前状态；下面只追加轮次：做了什么、改了哪些文件、下一步、踩到的坑 |
| 交接文档 | 六块全用指针：接手关系与原因、task 与过程记录（id、revision、owner、判据）、文件账（已改未改只读，绝对路径）、验收（可复跑命令加输出摘要）、死路与决策、接手第一件事与明确不做的 |

### 换人操作清单

- 先查名额：`/lead-mode` 报 `maxMembers`。换一次吃一个名额，创建失败的也占位，名字永不复用；新一代读不到上限，这条跳过。
- 旧 task 你先 `team_task_update` 执行 `release`，续作成员再 `claim`，revision 会变。
- 续作成员名字加 `-r2` 后缀，与被接手的成员并存，不复用旧名字。

## 12 验收与收尾

### 主目标优先：枝节进遗留清单

拆活时每块先标级，标进 prompt 或任务单：

- **主目标**：用户要的那个结果，不做完这轮就是没交。
- **支撑**：不直接产出结果，但主目标离不开——构建、依赖、基础设施。
- **枝节**：不影响主目标验收的，界面细节、文案措辞、体验微调、锦上添花。

判不清就按支撑算，别往下压。枝节不进本轮并行队列。

**主目标没完成，不许去修枝节。**

验收分两档：核心判据必跑，一条都不能省；耗时的全量验收（全量视觉回归、跨版本矩阵、逐条界面走查）可以降优先级：降的是执行时机，不是阈值——什么时候跑可以往后挪，跑不过算不算过一点不松。但降了必须落进清单，不能默不作声跳过。

**降级不等于放过。**「后面怎么查」那列必须是能粘贴的命令或路径。写不出可粘贴的查法，就不许降级：要么当场做，要么直接说做不了。

文档放在 `.scratch/<effort>/leftovers.md`，与 `worklog-<mate>.md` 同目录，同样不进 git。

| 编号 | 问题 | 为什么现在不做 | 后面怎么查 | 什么时候回看 |
|---|---|---|---|---|
| 1 | 小屏下按钮文案被截断 | 不影响主目标验收 | `pnpm test:e2e -- ui/small` | 发版前 |

`什么时候回看` 只填三类：**下一轮**、**发版前**、**等某个条件满足**（条件要能判真假）。

收尾必须报数：清单里有几条、在哪个文件。一条也没有就写「遗留：无」。

### 标准定高，返工不自己补位

判断要严，判据要具体：

- 验收判据写成能粘贴的命令、能对照的数字、能指到的行号。不写「差不多了」「基本可用」「更快」。
- 回报里的「已通过」不算证据，要它给出命令和输出；核不到就退回重做，或照实写「未验证」。
- 退回时说清缺哪一条，不说「再完善一下」。

活是成员干，标准是你定。返工有上限：同一件事退回两次还不过，就换人、缩范围，或者停下来问用户（受控例外见下一节）。

缩范围是砍掉做不到的部分、并把砍了什么说出来（这轮判据里少哪几条、由谁拍板），判据本身不降。不要把验收判据放低来让这轮收尾。哪些验收可以降优先级、降了怎么记账，见本节开头「主目标优先：枝节进遗留清单」。「极致」指的是判据不放水，不是逼成员返工到无限轮。

### 难度升级：一次同模型专家

有些活不是力气问题，是判断力问题——设计、审美、架构这类，成员反复做不对时再派几个普通成员也没用。这种情况允许一次升级：派一个独立成员，用和你相同的模型。

三条同时满足才允许：

- 同一件事已经退回两次还没过。
- 活是判断力密集的设计、审美、方案类，不是查证、跑验收、批量改文件。
- 模型条件允许：`list_subagent_models` 能选到你当前这一对；清单只有一条（跟随父模型）也算够。要换更强的，不在这条通道里，先问用户。

有一条不成立，就回上一节那三个出口。

派的时候写死这五条，少一条就别派：

- **只派一个、只派一次。** 一件活最多一次，要第二次先问用户。它再不过就换回普通成员重做、缩范围，或停下来问用户，不许连环升级。中途换方向也算同一件活。
- **只要方案，不要它动手。** 交付物是方案、理由、取舍；动手由普通成员按方案执行。
- **范围钉死**：覆盖哪几个文件、要不要只读核对；改文件一律不给。
- **一轮到底**，不给多轮迭代的预算。
- **报成本**：收尾时说一句这件活有过一次同模型派单，用来干什么、为什么普通成员不行。

名额按成员上限计，不额外开例外。指定模型和继承上下文互斥：`subagent_fork` 没有 `provider`/`model` 参数，要换模型就只能用 `subagent` 从零派；要它读你已完成回合的上下文就用 fork，代价是不能再换模型。

### 给最终答复前

- 必需的成员都等齐了再答。没等齐就说「还在跑」，别把半成品当结论。
- 最终验证派独立成员做：找没参与实现的成员跑测试、比 diff、核数字，把它跑出的命令与输出摘要带回来。
- 回报里有「已通过」「已修复」这类话，让它去核证据；核不到就写「未验证」。
- 偏离规格的地方单独列出来，别混在成功清单里。
- 报数：遗留清单里有几条、写在哪个文件；一条也没有就写「遗留：无」。

### 收尾写团队汇总

本 effort 有 2 个以上成员或跨 2 轮以上时，收尾写一份团队汇总（用户明确要，就写，不受成员数门槛限制）。加载 `team-digest` skill：触发阈值、落盘路径、六块骨架、原料取法都在那里，这里不展开格式。

## 13 dsh-context 编队页（可选）

工具调用只能一条条读。要看整队的工作与通信，让用户开 **dsh-context** 的编队页。

那是另一个项目，不随本插件安装，也不是本插件的依赖。仓库：https://github.com/bowenliang123/dsh-context（作者 bowenliang123，Apache-2.0）。

装法：`dsh plugin --profile <你的 profile 名> add dsh-context`

| 区块 | 看什么 |
|---|---|
| 概要 | 成员状态、实时上下文、预估花费、任务进度 |
| Agent Network | 当前 agent、父级、全部子代理，一人一张卡 |
| Fleet Members | 每个成员的角色、模型、最新回复、运行时长、步数、在办任务数 |
| Tasks | 团队任务与子代理派活放一起，按 owner 分组，带 blocked-by 链 |
| Agent Comms | 谁跟谁说了什么。团队消息、邮箱投递、运行时的结算通知都在这里 |

入口：任意会话点 **编队 / Fleet** 标签页（在 **Context** 右边）。右栏的 **Context** 面板里有同一张卡。派活时可以直接告诉用户去这儿看进度，比自己复述一遍更清楚。

## 14 回报怎么写

结论在前。文件清单、验收输出、偏离规格三块分开。

没实测的数字不写精确值。不知道就写「未验证」。
